# Customer segment operating manual

## Read and discover

1. Discover installed MCP tools and their current schemas on the selected customer OAuth connection. Honor product and role restrictions. No local credential, publisher proxy, session descriptor, or custom HTTP authentication belongs in this workflow.
2. Resolve names through `list_groups(query={"search":"name"})`; require an unambiguous ID. Read rules with `get_segment(segment_id="ID", include_schema=true)`. A static segment has explicit membership, not dynamic rules. Saved audience previews use `get_segment_contacts`; static membership uses `get_group_contacts`. Follow each discovered pagination schema. Do not silently add an active-contact filter to an unsaved count.
3. Discover capabilities using `list_segment_definition_facets(segment_id?)`, then `list_segment_definitions(segment_id?, query?, id?, category_type?, group_type?, group?, condition_type?, type?, include_details?)`. The `get_segment_definition` alias may be available. Compact results omit explicitly unsupported operators and support reasoning. The signed raw SDK catalog retains their metadata; never use an operator marked `isSupported: false` or edit the flag. Exact IDs, supported operators, values, request-backed choices, and feature gates come from live definitions, never examples.
4. Explain include/exclude branches, AND/OR between and inside cards, whole-card negation, nested conditions, event dates and counts. Mention unresolved definitions and unsupported comparisons explicitly.

## Prepare locally

Use Node.js with the packaged standalone SDK; no install or upstream checkout is required. `run_sdk.mjs` has no network or authentication client. Generated mutation modules execute local JavaScript, so review them first: only SDK calls and local helpers are allowed, with no imports, file/environment access, or network/persistence side effects. This runner is not a JavaScript security sandbox.

1. Call `list_segment_definitions(for_sdk=true, segment_id="ID")` for an edit, or omit `segment_id` for create/count. Never combine `raw=true` with `for_sdk=true`. The host downloads the exact returned `catalogRef.downloadUrl` to a local file using its ordinary download facility. It is a short-lived signed artifact URL, not an API authentication workaround; do not log/share it or add credentials. Save the exact `catalogRef` response separately. Do not follow a fabricated URL. If the host cannot retrieve this artifact, report SDK preparation blocked; compact definitions cannot replace the trusted catalog.
2. The runner verifies artifact bytes, SHA-256, catalog identity/version/expiry, organization, segment, and authoritative UI feature decisions. Refresh expired references through MCP. Never invent UI context or alter a catalog to enable a feature.
3. For update, save only the exact `schema` from `get_segment(..., include_schema=true)` to `sourceSchemaPath`. Confirm it is a dynamic segment in the selected organization. Backend-to-UI hydration is handled by the packaged SDK; unsupported conversion fails closed.
4. Write a focused default-exported mutation function using the nine public SDK methods. Require every mutation's `ok` result; return `segment.finish()` once. Use `find()` with exact cardinality for edits. Do not patch raw schema, `aggregate.rule`, `originOperator`, SDK internals, or output payloads.
5. Write a request JSON with `mode` (`create`, `update`, or `count`), `organizationId`, `catalogPath`, `catalogReferencePath`, and `mutationPath`. Update additionally requires `segmentId` and `sourceSchemaPath`; create requires `name` and may include `description` and `tags`. Paths resolve from the current working directory. Example invocation from plugin root:

   `node skills/segment-designer/scripts/run_sdk.mjs prepare request.json prepared.json`

6. Review `status: prepared`, `persisted: false`, validation, nonzero definition count, dependency-reset warnings, formula, and `hostCall.arguments.schema`. This artifact is a plan for a host operation, never evidence of remote completion. Keep contact data and catalog files private in a task output directory; none belong in the plugin package.

## Boolean, event, channel, and comparison semantics

The SDK supports include/exclude cards with AND/OR and negation, field conditions, custom events, ecommerce events, activity/widget activity, push/token, customer-data, lifecycle and predicted conditions when live definitions and feature gates permit them. See the SDK reference for full intents and atomic operations.

A rolling 90-day window uses the offered relative period operator (for example `{kind:"relative", operator:"LAST_DAYS", value:90}`), never a fixed calendar cutoff. Verify that this operator is offered by the selected date definition and that the account/event retention period permits 90 days. Some families have stricter available periods; do not silently shorten the requested window. Event identity, first/last date mode, occurrence/count and optional event parameters must be resolved together.

For channel behavior, use the offered activity event plus its exact media/channel criterion, or the appropriate push/token application and subscription field. An activity event alone does not imply email. Presence of an address or token does not imply consent, deliverability, or subscription; explain which property the condition actually tests. Activity requires an offered non-system criterion.

Scalar comparisons (equals, greater/less, ranges, occurrence count/rate, date-relative predicates) are limited to the chosen definition's operators. The SDK does **not** expose arbitrary SQL, field-to-field comparisons, comparing two event counts, ratios across aggregates, arbitrary nested Boolean expression builders, or event-sequence joins. Do not approximate “purchases greater than refunds” by two independent thresholds or rewrite an imported custom formula into a lossy card formula. State the precise unsupported predicate and ask for an acceptable supported alternative only if needed.

Use `scripts/extract_condition_operator_rows.mjs` for narrow operator-catalog lookups; its static semantics are guidance only. Live definitions remain authoritative.

## Host operations and verification

Use the corresponding discovered MCP tool for a requested remote change or count. Customer OAuth access for Yespo/eSputnik dynamic writes and unsaved counts was enabled by MCP #175 and verified in dentest. This does not establish every role or account's permission: honor actual denials and feature restrictions. Local preparation remains separate from a successful remote operation.

- **Create:** Reconcile an exact-name search before writing to avoid duplicate retry. Call `create_dynamic_segment(name, schema, description?, tags?)` using `prepared.hostCall.arguments`. Do not auto-reuse a same-name segment with different rules. Require a nonempty `segmentId`, `readback: "retrieved"`, and no unknown commit status, then independently read `get_segment(segment_id, include_schema=true)` and compare audience semantics. The backend may normalize UI JSON.
- **Update:** Immediately reread the source schema and compare its canonical hash with `baselineSha256` using the exported `verifyBaseline`. If changed, reload and prepare against the new baseline. Call `update_dynamic_segment(segment_id, schema)` with only the prepared schema. Require `updated: true`, a nonempty `segmentId`, `readback: "retrieved"`, and no unknown commit status; independently read back and check intended and untouched semantics. This precheck detects observed staleness, but is not an atomic backend compare-and-swap: another writer can race it.
- **Unsaved count:** Call **only** `count_segment_contacts(schema)`. Never create/update a segment to obtain a count. The pinned MCP waits for completion and returns `{totalCount, mediaChannels}` without a status field; accept this successful tool result only with a nonnegative integer `totalCount`. If a status field is present it must be `COMPLETED`; reject `error`/`isError` responses even when they contain a count. The exported `completedCount` enforces this contract and normalizes status to `COMPLETED`. Preserve `mediaChannels` if returned. Pending, failed, timed-out, denied, malformed, and unknown results are unavailable; zero is valid only in a completed response. The pinned server may wait up to 600 seconds and rate-limits attempts; do not automatically retry an unknown or timed-out calculation.
- **Saved audience freshness:** Saving changed conditions does not establish that the saved audience has been recalculated. The native editor requires **Recalculate** before comparing its saved count with the new rules. Report rule read-back and audience freshness separately; an unsaved schema count is not proof that saved membership refreshed. If the selected MCP exposes no recalculation operation, identify the native Recalculate step rather than inventing an endpoint or reporting a stale count as a failed save.
- **Uncertain writes:** Respect `commitStatus`, `retrySafe`, and returned IDs. Reconcile live state before any retry; retrieved readback alone does not establish that an uncertain update committed. Report what is and is not confirmed.

Static membership mutations are outside this local dynamic SDK flow. Do not infer membership changes from a request to inspect or count an audience.
